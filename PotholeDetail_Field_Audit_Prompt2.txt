BUG 1 — accident_risk_probability inconsistency between GeoJSON and detail paths
================================================================================

Two different computation methods produce potentially different values for the
same pothole depending on which endpoint serves the data.

  GeoJSON path (potholes.ts:75):
    accident_risk_probability = Math.round((probHigh + probCritical) * 1000) / 1000
    Computed CLIENT-SIDE from individual prob fields in the GeoJSON response.

  Detail path (potholes.ts:120-121):
    accident_risk_probability = raw.accident_risk_probability
    Read directly from the backend PotholeDetailResponse.

  Backend ML model (ml_models.py:47-52):
    proba = float(row.get("prob_high", 0) + row.get("prob_critical", 0))
    accident_risk_probability = round(proba, 3)

The ML model computes round(proba, 3) where proba = prob_high + prob_critical.
The frontend GeoJSON path does Math.round((probHigh + probCritical) * 1000) / 1000.
These are mathematically equivalent, but floating-point rounding between Python
and JavaScript can produce edge-case differences (e.g., 0.3005 rounding to
0.301 vs 0.300). The detail endpoint reads the backend's stored/rounded value
directly, while the GeoJSON path recomputes from the individual prob fields.
If there is any floating point difference between the stored prob_high +
prob_critical vs the stored accident_risk_probability, they will disagree.

FIX: Standardize on one approach. Either:
  (a) Use the backend value in both paths (remove client-side computation in
      mapGeoJSONProperties and read accident_risk_probability from GeoJSON
      properties instead), OR
  (b) Compute client-side in both paths (remove the field from
      PotholeDetailResponse and always compute from prob_high + prob_critical
      in the frontend).

BUG 2 — PotholeDetail type missing latitude / longitude
================================================================================

  PotholeDetail (types/index.ts:33) extends PotholeRecord, which does NOT
  include latitude or longitude. Pothole extends PotholeRecord and adds
  latitude + longitude.

  The component's prop type is Pothole | null (which includes lat/lng), but
  getPotholeById() returns PotholeDetail (which lacks lat/lng).

  In MapPage.tsx:104:
    const selectedPothole = selectedDetail ??
        potholes.find((item) => item.unique_key === selectedKey) ?? null;

  When selectedDetail resolves (user clicks a marker), it replaces the
  GeoJSON pothole. The result:
    - Before detail loads: pothole has lat/lng (from GeoJSON list)
    - After detail loads:  pothole loses lat/lng (from detail endpoint)

  The detail panel itself does not currently render lat/lng, but the PotholeMap
  component or getDistanceMiles() could be affected if selectedPothole is used
  for map centering or distance calculations.

  Additionally, the getPotholeById mapper (potholes.ts:101-133) does NOT map
  latitude or longitude from the backend response, even though
  PotholeDetailResponse includes them (inherited from PotholeResponse).

FIX: Either:
  (a) Add latitude/longitude mapping to getPotholeById():
        latitude: typeof raw.latitude === "number" ? raw.latitude : null,
        longitude: typeof raw.longitude === "number" ? raw.longitude : null,
      And add these fields to the PotholeDetail interface.

  (b) Better: merge detail data with the existing GeoJSON pothole instead of
      replacing it. In MapPage.tsx, instead of:
        const selectedPothole = selectedDetail ?? potholes.find(...) ?? null;
      Use:
        const basePothole = potholes.find(p => p.unique_key === selectedKey);
        const selectedPothole = basePothole
          ? { ...basePothole, ...selectedDetail }
          : selectedDetail ?? null;
      This preserves the GeoJSON lat/lng and augments with detail fields.

BUG 3 — aadt always null from detail endpoint
================================================================================

  PotholeDetail type (types/index.ts:15) includes:
    aadt?: number | null;

  getPotholeById mapper (potholes.ts:117) maps it:
    aadt: typeof raw.aadt === "number" ? raw.aadt : null,

  But PotholeDetailResponse (schemas.py:104-113) does NOT include aadt.
  It inherits from PotholeResponse which also does NOT include aadt. Only
  PotholeProperties (the GeoJSON schema) includes aadt.

  Result: aadt will always be null when fetched via getPotholeById(), even
  though the type allows it. Not rendered anywhere in the UI, so no visible
  bug, but it is a misleading type contract.

FIX: Either:
  (a) Remove aadt from PotholeDetail interface (since the detail endpoint
      never returns it), OR
  (b) Add aadt to PotholeDetailResponse schema and include it in the
      _map() function and the detail endpoint return.

BUG 4 — repair_eta sent but never used
================================================================================

  The backend computes repair_eta as an actual ISO date string (e.g.,
  "2025-03-15") in potholes.py:129-140:
    def _repair_eta(r: dict) -> str | None:
        fix_days = r.get("fix_days_estimate")
        created  = r.get("created_date")
        ...
        eta = base + timedelta(days=int(fix_days))
        return eta.strftime("%Y-%m-%d")

  The detail endpoint returns it (potholes.py:80):
    repair_eta = _repair_eta(pothole),

  PotholeDetailResponse includes it (schemas.py:108):
    repair_eta: Optional[str] = None

  But the frontend:
    - PotholeDetail type has no repair_eta field
    - getPotholeById mapper does not map repair_eta
    - PotholeDetail.tsx component does not read repair_eta

  Instead, the component shows "Repair ETA" as a day count using
  fix_days_estimate / predicted_repair_days (lines 119-127):
    value={
      pothole.fix_days_estimate !== null && pothole.fix_days_estimate !== undefined
        ? `${pothole.fix_days_estimate} days`
        : pothole.predicted_repair_days
          ? `${pothole.predicted_repair_days} days`
          : "N/A"
    }

  The backend already computed the actual date — the frontend ignores it and
  re-derives a less useful "X days" string.

FIX: Either:
  (a) Add repair_eta to PotholeDetail type, map it in getPotholeById(), and
      display the actual date in the component (e.g., "Est. repair: Mar 15"),
      OR
  (b) Remove repair_eta from PotholeDetailResponse and the _repair_eta()
      function to avoid computing unused data.

BUG 5 — Dead backend alias fields
================================================================================

  The _map() function in potholes.py:91-116 computes and returns these
  "frontend-friendly" alias fields that the frontend never consumes:

  Field                      | Value                        | Notes
  ---------------------------|------------------------------|---------------------------
  city                       | Always "New York"            | Not in frontend types
  zip_code                   | From DB row                 | Not in frontend types
  address                    | Composed "Street, Borough, NY"| Not in frontend types
  days_open                  | int(age_days)               | Alias for age_days
  impact_score               | Same as risk_score           | Alias for risk_score
  nearby_collision_count     | Same as nearby_crashes       | Alias for nearby_crashes

  These fields add response payload size for zero benefit. They are defined
  in PotholeResponse (schemas.py:80-100) and inherited by
  PotholeDetailResponse, so they appear in every pothole detail and list
  response.

FIX: Remove these fields from PotholeResponse and PotholeDetailResponse in
  schemas.py, and remove them from _map() in potholes.py. This reduces
  response size and eliminates confusion about which field name to use.

  If any frontend code might reference them in the future, add them to the
  TypeScript types at that time rather than maintaining dead aliases.
